## Implementation

Added in the AOSP tree under `device/google/cuttlefish/host/commands/vhal_proxy_server/`. The patch is [aaos16/patches/0002-vhal-proxy-server-kuksa.patch](../aaos16/patches/0002-vhal-proxy-server-kuksa.patch).

- `kuksa/KuksaMapping.{h,cpp}`: VSS↔VHAL conversion (pure functions).
- `kuksa/KuksaVehicleHardware.{h,cpp}`: Derives from `FakeVehicleHardware`. Reflects values into the property store from the KUKSA `Subscribe`. An HVAC `setValues` does a `Set` on the KUKSA actuator target and leaves the store unchanged until the state comes back. If it does not come back within 3 seconds, a `TRY_AGAIN` set error is reported. Reconnects at 1-second intervals.
- `kuksa/proto/`: the `kuksa.val.v1` proto (a copy from the provider side). The C++ stubs are generated by genrules in `Android.bp`.
- `vhal_proxy_server.cpp`: uses `KuksaVehicleHardware` if the environment variable `KUKSA_ADDR` is set, otherwise the previous Fake.
- `aaos16/docker-compose.yml`: added `KUKSA_ADDR=host.docker.internal:55555` and `extra_hosts: host.docker.internal:host-gateway`.

Design decisions:
- The Fake default config (`DefaultProperties.json`) already has all the properties of the mapping table, so `getAllPropertyConfigs()` was reused through inheritance instead of being written (a simplification of the original Planing.md idea). The other properties Car Service needs are also provided by the Fake as they are.
- Values are written with the store's `writeValue` directly (bypassing the access check of read-only properties).
- The total fuel capacity uses `INFO_FUEL_CAPACITY` = 15000 mL of the Fake (this resolves open issue 1 of Planing.md §7).

## Addendum: webcan HVAC ECU response

### Problem
The Gateway ECU puts an HVAC write on CAN as `AirconCommand` (0x526), but the simulator has no HVAC ECU to return the new state in `Aircon` (0x323). A write therefore never came back as state, and the VHAL value did not change (the earlier tests substituted this by rewriting the webcan Aircon by hand).

### Change
- Added HVAC ECU emulation (`_emulate_hvac`) to [auto-as-linux/autoas-as/src/tools/webcan/server.py](../auto-as-linux/autoas-as/src/tools/webcan/server.py). When a 0x526 frame is received, it is applied to the `Aircon` periodic sender (0x323).
  - Fields applied: `MM_AC_Cmd`→`AC_OnOff`, `MM_Def_Cmd`→`Defrost`, `MM_Fan_Cmd`→`FanLevel`, `MM_Temp_Cmd` (`CmdTargetTempRaw`≠0xFF)→`TargetTempRaw`, `CmdMode`→`Mode` (no gate bit).
  - Applied **only when the command value or its gate changed since the previous 0x526 frame** (edge behavior). The ECU keeps sending the same value with the gate asserted, so applying every frame would overwrite an Aircon state set by hand in the UI within 100 ms. `CmdMode` is applied on change only.
  - A swept Aircon is left alone. If there is no Aircon sender, one is created.
  - `GET/POST /api/hvac_emulation` switches it on/off (on by default).
  - Added an "HVAC ECU emulation" checkbox to the header of the browser UI ([static/index.html](../auto-as-linux/autoas-as/src/tools/webcan/static/index.html)). Changes made through the API are also picked up by 5-second polling. Confirmed with headless Chrome that clicking toggles it with the server state in agreement, and that a change made through the API shows up on the page.
- Added a description to [auto-as-linux/autoas-as/README.md](../auto-as-linux/autoas-as/README.md).
- Changed the write test of [aaos16/tests/kuksa_vhal_e2e.py](../aaos16/tests/kuksa_vhal_e2e.py) so that, without rewriting webcan by hand, it checks that the 4 items temperature, fan, A/C and air direction come back to the VHAL (it opens the webcan bus automatically if it is not open, and writes values that differ from the command currently on the bus to suit the edge behavior).

### Result
`kuksa_vhal_e2e.py` was run twice in a row with all items PASS. From the write to the VHAL value changing took about 0.1–0.3 seconds (VHAL → KUKSA target → provider → ECU → CAN 0x526 → webcan → 0x323 → ECU → provider → KUKSA → VHAL).

## Addendum: show AAOS temperature in °C

- Symptom: the AAOS HVAC bar showed °F. The cause is that the Fake VHAL default `HVAC_TEMPERATURE_DISPLAY_UNITS` is `FAHRENHEIT`. The KUKSA temperature (SYS-003) is in °C and so is the VHAL `HVAC_TEMPERATURE_SET`, so the values were correct and only the display unit differed.
- Runtime check: `cmd car_service set-property-value HVAC_TEMPERATURE_DISPLAY_UNITS 0 48` (CELSIUS=0x30) changed the bar to 20.5 / 24.0 (°C).
- Permanent fix: `KuksaVehicleHardware` sets `HVAC_TEMPERATURE_DISPLAY_UNITS` to CELSIUS at start-up (constant in `KuksaMapping.h`, agreement with the AIDL enum checked by `static_assert`). The patch (`0002-...patch`) was regenerated. Confirmed that it is `CELSIUS(0x30)` even after restarting Cuttlefish.
- The user can switch it back to °F in the AAOS settings or similar (it is an ordinary property). However, restarting Cuttlefish returns it to °C.
- Spec: added to SWARCH-003 §4.0.
